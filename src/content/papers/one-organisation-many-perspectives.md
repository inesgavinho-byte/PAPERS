Modern organisations live inside many applications.

One for projects.

Another for finance.

Another for clients.

Another for communication.

Another for documents.

Another for maintenance.

Another for reporting.

Each contains part of reality.

And gradually we begin to behave as if each part were a different reality.

It is not.

**Reality ≠ Representation.**

## The same event, five systems

Imagine a simple project change.

The client requests a modification.

The designer revises the drawing.

The contractor updates the price.

The supervisor validates it.

The finance team records the impact.

The same event may appear as:

a message;

a drawing revision;

a proposal;

an approval;

a budget change;

a task;

a line in a report.

The systems treat these as different objects.

But the underlying reality is one.

A change happened.

Everything else is a perspective on it.

## When representation begins to replace reality

A digital system has to simplify.

It cannot represent everything.

It chooses fields.

It chooses states.

It chooses categories.

It chooses what becomes visible.

That selection is inevitable.

The problem begins when we stop noticing that it happened.

A dashboard shows 80% completion.

But 80% of what?

Cost?

Time?

Tasks?

What has actually been built?

A percentage is not reality.

It is a projection onto reality according to a particular rule.

When we forget that difference, we begin managing the representation instead of managing what it represents.

## Departments are perspectives too

Fragmentation does not begin with software.

It often begins inside the organisation itself.

Finance sees cost.

Legal sees obligation.

Operations sees execution.

Commercial sees relationships.

Design sees intention.

Leadership sees risk, decision and priority.

None of these perspectives is wrong.

None contains the whole organisation either.

The problem appears when one perspective begins to behave as if it were the whole.

That is how locally correct decisions become globally absurd.

## One reality can have different states depending on the question

There is another difficulty.

The same object can have different states without contradiction.

A change can be:

approved from the client's perspective;

pending from a contractual perspective;

priced from a financial perspective;

not executed from the construction perspective.

If we try to reduce all of this to one field called “status”, we lose information.

Not because the data is insufficient.

Because the model is poor.

Reality does not necessarily have one single state.

It can have several valid states, each relative to a clearly defined perspective.

## The mistake of systems that try to own reality

Many digital applications are built as small closed universes.

Each creates its own client.

Its own project.

Its own document.

Its own person.

Its own task.

Then we try to synchronise those universes.

We duplicate identifiers.

We map fields.

We resolve conflicts.

We create integrations.

And we call interoperability the effort required to reconcile realities that should never have been separated in that way.

Perhaps the problem is not only that we need better integrations.

Perhaps we should assume from the start that identity belongs to reality, and that each system observes only part of it.

## This distinction shaped an important part of DECIMA

In DECIMA, I began to think about the problem differently.

If the same person appears in several applications, I do not want to create several people and reconcile them later.

I want to recognise one identity and allow several representations of that identity.

If the same project is seen through operations, finance, documents and communications, I do not want four projects.

I want one project with multiple perspectives.

This difference sounds semantic.

It is architectural.

It means separating reality from the systems that observe it.

It means allowing an application to be a lens rather than an owner.

And it means that an improvement in a shared capability can benefit several applications without requiring each of them to rebuild the same infrastructure.

## THREAD is a perspective, not the whole world

THREAD made this idea especially concrete.

Communication is an essential perspective on organisational reality.

It is not the whole reality.

A message can reveal that a decision was discussed.

It does not, by itself, prove that the decision was formally approved.

An email may explain why a change happened.

It does not necessarily replace the drawing, the contract or the execution.

The value of THREAD is not in turning communication into the absolute source of truth.

It is in connecting communication to the other perspectives needed to reconstruct the event.

The same logic applies to any specialised system.

A perspective is powerful precisely when it knows its limits.

## The problem with universal dashboards

Organisations repeatedly fall for the idea of a dashboard where “everything is”.

It is an appealing promise.

One page.

One view.

One truth.

But complex organisations do not need one single view.

They need coherence between views.

Leadership needs synthesis.

An operational team needs detail.

Someone responsible for contracts needs validity and obligation.

A project team needs versions, decisions and dependencies.

Forcing all of these people to look at the same surface does not create alignment.

It may simply reduce every perspective to the lowest common denominator.

## Good architecture allows disagreement without losing identity

Two teams may disagree about how to interpret an event.

That does not mean we should create two realities.

We should preserve:

the event;

both interpretations;

who produced them;

when;

with what authority;

and what decision, if any, resolved the divergence.

A mature system does not need to erase disagreement to create coherence.

It needs to represent disagreement without losing the identity of what is being disputed.

## Artificial intelligence needs perspective too

AI makes this problem even more important.

An agent may have access to finance, documents, communications and operations.

That does not mean every source should be treated in the same way.

Nor should every question receive the same composition of context.

The question defines the perspective.

“How much did it cost?” requires one evidence architecture.

“Why was it changed?” requires another.

“What remains undecided?” requires another.

“What was actually executed?” may require combining several.

A good agent does not simply need more context.

It needs to understand which context is relevant to the perspective being asked for.

## Unity does not require uniformity

There is an understandable fear that a common architecture will make everything the same.

It should not.

A unified organisation does not need one application.

It does not need one interface.

It does not need one operating model.

It needs enough shared identity, relationships and rules for its different parts to keep referring to the same reality.

Unity is not on the surface.

It is in the underlying coherence.

## Reality first

Perhaps the order should be this:

first, understand what exists in reality;

then define the relationships that need to be preserved;

then build the different perspectives required to act upon that reality.

Do not begin with the application.

Do not begin with the dashboard.

Do not begin with the department.

Begin with what exists.

A person.

A project.

A building.

A decision.

An obligation.

An event.

Only then ask how each system needs to observe it.

## One organisation. Many readings.

Organisations do not need to eliminate perspectives.

They need to stop confusing them with independent realities.

Finance will continue to see cost.

Design will continue to see intention.

Operations will continue to see execution.

Legal will continue to see obligation.

Communication will continue to reveal relationships and commitments.

That is desirable.

But underneath those readings there must be enough continuity for us to know that we are talking about the same thing.

**Reality is one.**

**Systems are perspectives on it.**
